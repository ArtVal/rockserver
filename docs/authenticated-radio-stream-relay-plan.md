# Authenticated radio stream relay — план реализации

**Статус:** RR-001 реализован локально и прошёл обязательные проверки; RR-002—RR-006 остаются планом.

## Цель и границы

RockServer получает поток станции и отдаёт его только залогиненному пользователю с действующей браузерной сессией или авторизованному устройству с действующей native device session. Клиент выбирает станцию по `station_id`; исходный URL сервер берёт только из каталога/БД. Клиентский URL или redirect target никогда не служит источником доверия. Relay нужен Web, ESP32, RockCast и RockMobile, в том числе когда прямой доступ клиента к станции неудобен.

Существующий RockCast LAN relay для Cast и состояние плеера в device control — отдельные функции. ICY `now-playing` сообщает, что передаёт радиостанция; фактическое воспроизведение подтверждает сам плеер. В первой версии аудио передаётся без транскодирования: codec, container и bitrate upstream должны поддерживаться клиентом.

## Контракт и поток данных

```text
Radio station -> RockServer (catalog lookup, safe upstream, ICY parser)
                            |-> authenticated GET /api/v1/stations/{station_id}/stream -> player
                            `-> now-playing snapshot + SSE -> Web UI
```

- `GET /api/v1/stations/{station_id}/stream` проверяет действующую browser cookie или native Bearer session до DNS lookup и открытия upstream. Browser использует same-origin `<audio src=...>` и HttpOnly cookie; native клиенты передают Bearer в заголовке. Не помещать bearer/session в URL. Отозванные/истёкшие сессии не допускаются к новым подключениям; для уже открытых соединений определить ограниченный срок жизни и повторную авторизацию при reconnect.
- Сервер выбирает действующую primary stream запись станции в БД; неизвестная/недоступная станция или неподходящий URL дают обычную ошибку до начала ответа. Не принимать `url`, `streamUrl` или аналогичный параметр запроса. Каталоговые `streamUrl` могут оставаться ради обратной совместимости; переход клиентов на relay не требует немедленного удаления поля.
- Relay сохраняет аудиобайты и совместимый `Content-Type`, не перекодирует и не буферизует поток целиком. Он запрашивает ICY у upstream, читает `icy-metaint` и ограниченный `StreamTitle`. Клиенту, который запросил `Icy-MetaData: 1`, relay передаёт ICY-блоки и `icy-metaint`: RockCast, RockMobile и ESP32 могут показывать трек из самого потока, как сейчас делают клиенты с прямым подключением. Остальным отдаёт чистое аудио; Web получает название из server-side snapshot/SSE, поскольку обычный `<audio>` не предоставляет JavaScript удобный доступ к ICY. Сохранять `rawTitle`; `artist`/`title` — необязательная эвристика, `updatedAt` — момент наблюдения. Если ICY нет, аудио продолжает работать, а metadata помечается отсутствующей/устаревшей.
- Минимальный baseline защиты обязателен уже в RR-001 **до** outbound: только HTTP(S), без userinfo, проверка DNS и фактического IP, запрет loopback/private/link-local/metadata и других внутренних адресов; каждый redirect проверяется заново. Ограничить время соединения, размер заголовков/metadata, число redirects и одновременных подключений. RR-005 расширяет и проверяет эти ограничения, а не впервые вводит SSRF-защиту.
- При EOF/сетевой ошибке upstream текущий audio response завершается; не склеивать новый поток с прежним HTTP-ответом. Клиент повторно подключается с ограниченной экспоненциальной задержкой и jitter, прекращает попытки при 401/403 и уважает 429/`Retry-After`. Сервер делает ограниченные попытки открытия upstream до выдачи первого байта и освобождает соединение при уходе последнего клиента. Устаревшее now-playing не выдавать за свежее.

## Now-playing и события

Отдельный канал нужен прежде всего Web UI: `<audio>` воспроизводит звук, но не отдаёт странице `StreamTitle`. Планируемый `GET /api/v1/stations/{station_id}/now-playing` возвращает последний snapshot с `stationId`, `rawTitle`, nullable `artist`/`title`, `updatedAt` и признаком свежести/отсутствия. Планируемый `GET /api/v1/stations/{station_id}/events` передаёт начальный snapshot и изменения через SSE; WebSocket для односторонних обновлений не нужен. Оба endpoint используют те же session/ownership правила и лимиты, что stream. Native плеерам отдельное metadata-соединение не требуется, если они читают ICY из relay stream. В v1 с отдельными upstream на клиента snapshot станции — best effort: разные upstream могут быть смещены во времени; RR-006 делает источник единым.

## Этапы для отдельных задач Codex

Порядок ниже обязателен; каждый этап начинать с проверки актуального кода, `AGENTS.md`, `docs/status.md`, `docs/tasks.md` и `api/openapi.yaml`. HTTP-контракт обновлять в OpenAPI вместе с реализацией. Серверный и клиентские репозитории менять отдельными задачами.

### RR-001 — authenticated relay + ICY metadata

Реализовать station-ID endpoint, авторизацию browser/native sessions, DB lookup primary stream, прямую передачу аудио и ограниченный ICY parser. Добавить baseline SSRF/redirect/IP validation, resource limits, timeout/cancellation и описанную политику разрыва/reconnect. Хранить последний ограниченный metadata snapshot активного relay. **Готово, когда:** без сессии и с client-supplied URL upstream не открывается; локальный fake upstream доказывает передачу ICY запрашивающему клиенту, чистого аудио остальным и получение `rawTitle` сервером; отсутствие/битый ICY не ломает звук; disconnect освобождает ресурсы.

### RR-002 — metadata API/events

Опубликовать snapshot и SSE для Web UI с тем же auth, bounded subscribers и начальным значением при подписке. Договориться о stale/empty состоянии и об ошибках reconnect. **Готово, когда:** новый подписчик сразу получает актуальный snapshot, смена `StreamTitle` доставляется без перезапуска stream, чужая/неавторизованная сессия не получает данные, после обрыва подписка корректно восстанавливается.

### RR-003 — Web, RockCast и RockMobile

Перевести playback этих клиентов на relay URL; Web берёт now-playing из snapshot/SSE, RockCast и RockMobile продолжают читать ICY из аудиопотока. Оставить существующие локальные/offline fallback по политике каждого клиента. Web использует browser session без токена в URL. **Готово, когда:** каждый клиент играет поддерживаемый codec через RockServer, показывает исходный `rawTitle` или разобранные artist/title, реагирует на смену трека и на 401/429/network failure. Клиентские изменения выполнять в соответствующих репозиториях.

### RR-004 — ESP32

Использовать существующую авторизованную device session для HTTP stream; при поддержке ICY читать название из того же соединения, без обязательной подписки на SSE. Учитывать ограниченную память: streaming без накопления полного ответа, bounded buffer и управляемый reconnect; на устройствах с дисплеем показывать now-playing. **Готово, когда:** ESP32 играет поток через RockServer без VPN, обновляет экран при смене трека и восстанавливается после краткой потери сети; отзыв device session прекращает новые подключения.

### RR-005 — security hardening

Проверить весь outbound путь против DNS rebinding, redirect к внутренним адресам, IPv4/IPv6 и нестандартных ответов; закрепить IP фактического соединения после проверки. Настроить per-account/device/IP rate и connection limits, global upstream budget, медленных клиентов, idle/read timeouts, ограничения ICY/HTTP заголовков и безопасные логи/метрики без токенов и stream URL. **Готово, когда:** локальные негативные тесты закрывают redirect/IP обходы и исчерпание лимитов; перегрузка даёт контролируемую ошибку без утечки ресурсов и не затрагивает чужие сессии.

### RR-006 — shared upstream relay

Заменить отдельный upstream на клиента одним активным upstream на станцию с bounded fan-out, единым ICY parser и metadata snapshot/events. Сохранить выдачу ICY запрашивающим клиентам и чистого аудио остальным. Медленного клиента отключать или применять явную bounded backpressure policy, не задерживая остальных; закрывать upstream после ухода последнего слушателя и короткого idle окна. **Готово, когда:** несколько клиентов одной станции вызывают один upstream; смена трека доходит до всех по выбранному для них способу; медленный/отключившийся клиент не блокирует остальных; upstream и память освобождаются после idle.

## Передача задачи

Для каждого RR-этапа передавать в Codex только его секцию и зависимости, просить сначала сверить фактический код и затем реализовать критерии готовности с детерминированными локальными проверками. Фактическое состояние и результаты проверок фиксируются в `docs/status.md`. Следующий шаг — RR-002.
